# ROCOS-App 版本维护

遵循 [SemVer 2.0.0 中文规范](https://semver.org/lang/zh-CN/)。以下 alpha/beta/rc 的用途是本仓库约定，并非 SemVer 强制规定。

## 当前发布周期

- 原工作区版本为 `3.0.0`，用户说明仍有较多 bug，尚处于发布前测试阶段；不要据此宣称 `3.0.0` 已正式发布。
- 当前目标正式版为 `3.0.1`，首次内部测试编号为 `3.0.1-alpha.1`。实际当前值始终读取根目录 `CMakeLists.txt`，不要每次重新设为首次编号。
- 确认本次为内部测试更新后，将 `3.0.1-alpha.N` 更新为 `3.0.1-alpha.(N+1)`。每个提交或独立待交付内测版本递增一次，已为本次提交准备且符合确认类型的版本更新直接复用，不按修改文件数、编译次数或验证重试次数递增。
- 默认维持 alpha 阶段。仅在用户要求切换测试阶段时使用 `beta.1` 或 `rc.1`，同阶段继续递增编号；不因单元测试通过而自动切换阶段或发布正式版。
- 正式 `3.0.1` 仅在用户确认测试稳定并要求准备正式版本时去掉后缀。记录实际验证结果及尚未完成的硬件/模拟器验证，不推断机器人运行稳定。
- 此周期结束后，以最新版本和新的发布目标为准，不再固定使用 `3.0.1`。

版本顺序示例：

```text
3.0.0 < 3.0.1-alpha.1 < 3.0.1-alpha.2 < 3.0.1-beta.1 < 3.0.1-rc.1 < 3.0.1
```

不要使用低于 `3.0.0` 的 `3.0.0-alpha.N` 表示本轮后续内测，也不要使用 `3.0.0.1` 或用 `+build.N` 代替内测序号。构建元数据不影响 SemVer 优先级；数字部分和纯数字预发布标识符不加前导零。

## 版本来源与修改范围

根目录 `CMakeLists.txt` 是版本的唯一维护来源：

| 内容 | 维护方式 |
| --- | --- |
| 数字版本 | `project(rocos_app VERSION X.Y.Z ...)`，CMake 此处只接受数字版本 |
| 预发布后缀 | `ROCOS_APP_VERSION_PRERELEASE`，例如 `alpha.2`；正式版设为空字符串 |
| 完整版本 | `ROCOS_APP_VERSION_FULL`，由上述两项拼接，不另行硬编码 |
| C++ 版本宏 | `include/ver.h.in` 中数字宏使用 CMake 数字分量，`ROCOS_APP_VERSION` 使用完整版本 |
| 生成头文件 | CMake 在构建目录生成 `ver.h`，验证生成结果，不直接修改 |

不要全仓库替换数字版本：`config/rocos-API.yaml` 中 `openapi: 3.0.0` 是 OpenAPI 规范版本，`info.version` 是独立 API 文档版本；第三方依赖、历史文档、已有 Git 标签同样不能批量改动。仅在版本策略或发布阶段变化时更新 README 的阶段说明，日常 alpha 序号无需在文档中重复维护。

## 确认更新类型与最终版本

每次提交先从本次指令或仍明确适用于本次提交的指令中确定更新类型。用户已明确要求“内部测试更新”“patch 更新”或给出无歧义的目标版本时，直接按要求处理，不重复询问。仅说“创建提交”“修复 bug”，或仓库当前处于 alpha 阶段，都不算明确选择更新类型；历史上某次提交选择内测也不自动沿用到后续提交。

指令未明确时，先读取实际版本并检查变更，再询问：“本次提交选择内部测试更新还是 patch 更新？”同时给出根据下表算出的候选版本。说明这是本 skill 的提交前确认要求，并附上本文件链接。等待用户答复期间可继续审查和验证，但不决定最终版本、不修改版本源、不创建提交；不能因等待超时而默认选择内测。

| 已确认的意图 | 规则 | 示例 |
| --- | --- | --- |
| 内部测试更新，当前为预发布版 | 保持核心版本和阶段，仅增加序号 | `3.0.1-alpha.1` → `3.0.1-alpha.2` |
| 内部测试更新，当前为正式版 | 为下一补丁周期创建首次内测版本 | `3.0.1` → `3.0.2-alpha.1` |
| patch 更新，当前为预发布版 | PATCH 加一，保留测试阶段并将序号重置为 1 | `3.0.1-alpha.1` → `3.0.2-alpha.1` |
| patch 更新，当前为正式版 | PATCH 加一 | `3.0.1` → `3.0.2` |
| 明确要求测试稳定后转正式版 | 保留目标核心版本，去掉预发布后缀 | `3.0.1-alpha.N` → `3.0.1` |

预发布阶段的 patch 更新会改变本轮目标正式版，报告中明确指出这一变化；“patch 更新”本身不代表测试稳定或授权转正式版。若用户指定的版本与更新类型、稳定性要求或 SemVer 兼容性判断冲突，说明具体冲突并询问，不静默覆盖其意图。用户给出明确目标版本时优先核对该版本，不再额外递增。

确认类型后，说明“旧版本 → 最终版本”和计算依据，再修改文件。已有明确指令或用户已回答上述问题时，无需再次请求相同确认。仍须遵守下文的兼容性检查，不能用内测或 patch 选择掩盖 MINOR/MAJOR 级别变化。

## 每次 Git 提交前

- 创建每一个 Git 提交前都执行本 skill，包括仅文档、测试、构建配置和维护类提交。用户授权提交时，版本检查和更新是提交准备的一部分；按上节确认更新类型后确定最终版本，不能自动选择内测更新。
- 对比 `git show HEAD:CMakeLists.txt`、`git show :CMakeLists.txt` 与工作区版本，结合 `git diff --cached` 确定实际待提交内容。首次引入版本维护机制时，以已准备好的初始内测版本为准。
- 若本次提交尚未更新版本，按已确认的更新类型、发布阶段和兼容性规则更新；若已为本次提交准备了合法且高于父提交的版本，还须核对其符合已确认的更新类型，再验证复用。提交失败后重试不再次递增或重复询问；连续创建多个新提交时，每个提交分别更新版本，更新类型仅在用户明确覆盖这些提交时统一沿用。
- 将版本变更与本次业务或文档变更放在同一提交，不再为版本更新额外创建一个提交。暂存时只纳入本次授权范围内的变更和必要版本修改；`CMakeLists.txt` 有无关改动时按块暂存，不能整文件带入。提交前核对暂存区中的版本源及模板一致性，并执行 `git diff --cached --check`。
- 提交完成后核对提交中的实际版本，并在结果中说明版本变化。此规则是代理的提交工作流，不是 Git hook；不会自动拦截用户在终端或 IDE 中手动创建的提交，也不构成主动提交或发布的授权。

## 执行流程

1. 阅读仓库 `AGENTS.md`，检查 `git status --short`、相关差异、当前版本和本地标签。保留用户已有改动，不将未提交内容误称为已发布。仅查看本地标签不能证明远端没有同名版本。
2. 按“确认更新类型与最终版本”一节，从明确指令或用户答复中确定本次类型和版本，不默认内测更新。已经交付的版本不覆盖、不复用。准备实际发布时，在用户授权的远端范围内核对同名标签/发行是否存在。
3. 检查兼容性：公共契约包括面向调用方的 C++ 接口、HTTP 路由/JSON 请求响应及错误码、Lua 脚本接口，以及已文档化的配置行为。兼容 bug 修复增加 PATCH，兼容的新功能或弃用增加 MINOR 并清零 PATCH，不兼容公共 API 修改增加 MAJOR 并清零 MINOR/PATCH。不要只根据提交前缀判断。
4. 当前 `3.0.1` 目标适用于兼容修复。若变更需要 MINOR/MAJOR，说明具体契约变化与目标的冲突，提出对应版本，待用户决定拆分变更或调整发布目标；不要把不兼容改动伪装成补丁。
5. 修改版本源，确保模板使用完整版本；按变更内容整理简短版本说明，不编造修复项或测试结果。单纯说明版本规则或检查版本且不准备提交时不修改版本号。
6. 验证后报告旧版、新版、阶段、修改位置及验证结果。更新版本文件不等于创建标签或发布；只在用户已授权相应操作时提交、打标签、推送或创建 Release。标签采用 `v<完整版本>`，版本字符串本身不带 `v`；预发布 Release 标记为 prerelease。

## 验证

- 运行 `git diff --check`。
- 运行 `cmake -S . -B build`，检查输出的 `ROCOS-App version` 和生成的 `build/ver.h`：完整字符串包含预发布后缀，数字宏与目标核心版本一致。
- CMake 配置会复制运行配置到构建目录。优先使用独立临时构建目录验证，避免覆盖正在使用的运行配置；依赖缺失时如实报告配置失败及有限验证结果。
- 仅版本和 skill 文档变动无需运行机器人或增加 C++ 行为测试。涉及实际功能修复时，按仓库指南运行相关构建和回归测试；硬件使能或运动测试仅在明确准备好的硬件/模拟器环境中执行。
- 准备正式版本时核对本轮修复的验证记录、已知问题和用户的稳定性结论；缺少证据时列明缺口，保持预发布身份。
